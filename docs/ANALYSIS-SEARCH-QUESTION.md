# 拍题搜题模式（小猿搜题 / 快对式）可行性分析

> 目的：评估把当前「AI 错题本」升级为「拍照搜题 → 匹配题库 → 返回答案/解析」的可行性。
> 状态：**仅分析，不实施。**

---

## 1. 目标形态 vs 当前系统

### 小猿搜题 / 快对 的形态
```
拍一张题 → 识别题目（OCR）→ 题目指纹/归一化 → 在【海量题库】检索 → 返回【原题 + 答案解析】
```
核心是「**从题库库里找到这一道原题，把它的答案和解析给你**」。

### 当前系统（AI 错题本）的形态
```
拍一张题 → 识别题目（OCR）→ AI 结构化 → 【存入自己的错题本】
（附带：同类题匹配 = 在【自己的题库】里找相似的）
```
核心是「**整理自己拍的错题**」，不是「搜题」。

| 能力 | 当前系统 | 搜题模式 | 差距 |
|---|---|---|---|
| 拍照/OCR | ✅ RapidOCR + 视觉兜底 | ✅ 需更高准确率 | 小 |
| 题目识别/结构化 | ✅ 已有 | ✅ | 小 |
| 题库检索 | ⚠️ 仅自己错题（几十道） | 需**百万级题库** | **大** |
| 题库数据 | ❌ 无 | 需**海量题目+答案** | **最大** |
| 答案解析 | ✅ AI 现解（DeepSeek） | 题库自带（更准）或 AI | 中 |
| 用户系统/云端 | ✅ 已有 | ✅ | 无 |

---

## 2. 核心能力拆解与差距

拍题搜题要打通 4 个环节：

### 2.1 题目识别（OCR → 文本）
- 已有 RapidOCR（印刷体）+ 后端视觉兜底（DeepSeek 读图），**基本够用**。
- 差距：小猿对手写/模糊/复杂排版优化更好；数学公式 LaTeX 化需要更稳。属于「可优化，非阻塞」。

### 2.2 题目归一化与指纹（把题目变成可检索的键）
- 把 OCR 文本 → 去噪（去除题号/空格/乱码）→ 题干 LaTeX 规范化 → 生成**指纹**（字符 n-gram + 哈希 / 向量）。
- 当前系统有 `compose_embedding_text`（stem+知识点）做向量，可扩展为更精细的题目指纹。
- **技术难度：中**，有现成库和思路可做。

### 2.3 题库检索（在百万级里找到原题）
- 当前用 ChromaDB（向量）+ 标签匹配，适合「几万~几十万」题量。
- 百万级需要：加**全文索引（SQLite FTS5 / BM25）** + 向量库调优，或换 ES/专用检索。
- **技术难度：中**，可增量扩展。
- 关键是**匹配置信度阈值**——匹配错了会给错答案，必须设召回精度门槛。

### 2.4 答案与解析来源 —— 这是和「AI 错题本」的根本区别
- 搜题的价值在于「**这一道原题**的权威答案」，不是 AI 现算。
- 来源只有三条路：
  1. **自建题库**（积累/爬取/购买）——规模、版权、成本是硬门槛；
  2. **题库自带答案**（最优，但你没有题库）；
  3. **AI 现解**（当前系统已能做，但答案可靠性、格式、超纲题不如题库）。

## 3. 可行性分维度评估

### 3.1 题库数据 —— ⚠️ 最大瓶颈（决定性）
| 来源 | 可行性 | 问题 |
|---|---|---|
| 开源题库（GitHub 等） | 部分可行 | 数量少（几百~几万），质量参差，科目不全，多为竞赛/高考题 |
| 爬取公开题目网站 | 技术可行 | **版权风险高**（小猿/快对自身就有教辅侵权的法律纠纷史）；且多为图片需二次识别 |
| 商业题库授权 | 贵 | 教育题库 API 通常按量/授权收费，成本高 |
| 用户自积（错题本） | 成本低 | 量太小（几十~几百道），覆盖不了随机拍题 |
| AI 生成+人工校验 | 不可靠 | 生成的"题"与原题对不上，失去搜题意义 |

> **结论**：题库是搜题模式的**命门**。没有百万级+带答案的题库，「搜原题给答案」就无从谈起。这是和小猿/快对竞争的**核心资产壁垒**，也是它们花重金积累多年+版权诉讼不断的原因。

### 3.2 识别与匹配技术 —— ✅ 可行（有基础）
- OCR、结构化、向量检索都已有雏形，增量开发可控。
- 主要工作：题目指纹、全文索引、匹配置信度、大规模检索性能调优。

### 3.3 版权 / 法律 —— ⚠️ 高风险（尤其商业化）
- 题目文本、答案、解析的版权归属复杂（国内教辅版权近年争议多）。
- **自用/内测**：爬取风险相对可控（不对外分发）。
- **商用分发**：几乎必然面临题库版权问题，需谨慎授权。

### 3.4 成本与部署
- 计算：OCR + 检索在现有 CVM（1.9G 内存）可跑小规模；百万级题库 + 高频查询需要**更大内存/加机器**（ChromaDB 全量内存索引、ES 需独立服务）。
- 存储：百万题 JSON/向量 ≈ 数 GB 级，现 CVM 不够。
- 推理：AI 解题走 DeepSeek（按 token 计费），题库命中则零推理成本。

### 3.5 工作量（按阶段）
- **阶段 A「AI 直接解题」**（拍题→识别→DeepSeek 给答案）：当前系统几乎已具备，小改动。
- **阶段 B「自建小题库 + 检索」**（把错题/手动录入的题做成可检索库）：中等，几周。
- **阶段 C「规模化搜题」**（百万题库 + 原题匹配）：**大**，且受限于数据源。

---

## 4. 分阶段实现路线（如决定做）

### 阶段 A：拍题 → AI 直接解题（推荐先做）
- 当前系统已能识别 + AI 结构化；只需加「解题」输出（DeepSeek 解出答案+解析）。
- 不需题库，最快见效，先解决「拍题给答案」的体验。
- 局限：AI 现解，对超纲/偏题/争议题可能不准。

### 阶段 B：自建可检索题库（面向自己的错题/精选）
- 把错题本 + 手动录入做成带答案的题库，检索用「自己库内原题」优先。
- 对你个人重复复习有价值，量小但能用。

### 阶段 C：规模化题库（慎重评估）
- 仅在确定数据源（授权/合规爬取）且能支撑存储计算时推进。
- 否则停留在 A/B，避免踩版权和成本坑。

---

## 5. 结论与建议

**技术可行性：中高。** OCR、结构化、向量检索、AI 解题你都已经有基础，增量实现「拍题 → 识别 → 检索/AI 出答案」是**做得出来的**。

**商业/数据可行性：低-中。** 真正的分水岭在**题库数据**：
- 小猿/快对的核心资产是「百万级带答案的题库 + 版权授权」，这不是技术问题，是数据与合规壁垒；
- 没有题库，「搜原题给权威答案」不成立，只能退而求其次「AI 现解」。

### 我的建议
1. **先做「阶段 A」**：拍题 → 识别 → DeepSeek 直接解题给答案+解析。**工作量小、立即可用**，体验上已经接近搜题（虽然答案来自 AI 而非题库）。
2. **加「阶段 B」**：把自己的错题/录入题做成可检索库，自己库里有的先匹配原题（你复习最有价值）。
3. **阶段 C（规模化题库）暂时不做**：除非你确认了数据源和版权/成本能承受，否则不建议投入。

> 一句话：**做成「AI 解题的拍题体验」很现实、很快；做成「小猿式海量原题搜题」的难点不在技术、在题库数据和版权。**
